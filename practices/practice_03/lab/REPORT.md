# Отчёт: практика 3 — локальная модель как агент-помощник

## 1. Железо и окружение

- **CPU:** Intel Core i5-13420H (13th Gen), 8 ядер / 12 потоков
- **RAM:** 16 ГБ (из них ~2 ГБ ушло под swap при тестах — машина под нагрузкой)
- **GPU:** нет дискретной видеокарты, только интегрированная Intel UHD Graphics (Raptor Lake-P). Инференс **полностью на CPU**.
- **Ollama:** версия 0.34.4
- **OpenCode:** версия 2.0.15 (провайдер `ollama` через OpenAI-совместимый endpoint `http://localhost:11434/v1`)

## 2. Почему `qwen2.5:3b-instruct`, а не `qwen3.5:4b`

Изначально планировалось использовать `qwen3.5:4b` (есть в `experiment.py` как значение по умолчанию, и `Modelfile.agent` собран именно на нём). На практике это не сработало:

- `qwen3.5` — "thinking"-модель: она генерирует блок рассуждений перед финальным ответом. Через прямой `/api/chat` Ollama это контролируется флагом `think: false` (как в `experiment.py`), и там всё было нормально.
- Но OpenCode подключается к Ollama через **OpenAI-совместимый endpoint** (`/v1/...`, провайдер `@ai-sdk/openai-compatible`). Этот слой не умеет выключать thinking-режим `qwen3.5` штатным способом — `think: false` в `options` не добирается до модели так, как через нативный Ollama API. В результате модель на каждый запрос уходила в длинные внутренние рассуждения.
- На железе без GPU (чистый CPU-инференс) это выливалось в **зависания на 5–35 минут на один ответ** в сессиях OpenCode — не ошибка, а буквально ожидание, пока модель домотает мысленную цепочку перед выводом текста. Для интерактивной работы и тем более для автоматического прогона 5 вопросов это неприемлемо.
- Пробовали `qwen3.5:2b` — та же проблема (это тоже thinking-модель, просто поменьше).
- В итоге перешли на `qwen2.5:3b-instruct` — instruct-модель без режима thinking вообще, отвечает сразу финальным текстом. Время ответа на тот же CPU — секунды, а не десятки минут.

**Вывод:** при выборе локальной модели под инструмент с OpenAI-совместимым слоем важно заранее проверять, что отключение thinking реально работает через тот транспорт, которым будет идти трафик, а не только через нативный API модели.

## 3. Итоговая конфигурация

- **Базовая модель:** `qwen2.5:3b-instruct`
- **Квантизация:** стандартная для тега `instruct` из библиотеки Ollama — Q4_K_M (4-бит, k-quant), как её публикует Ollama по умолчанию для этого тега.
- **Контекст:** `num_ctx 4096` (см. `Modelfile:2`) — на малом учебном репозитории этого достаточно; в `opencode.json` агенту `itmo-agent` выставлен лимит контекста 65536/output 256 на уровне интерфейса модели, но фактическое окно инференса ограничено `num_ctx` модели.
- **Температура:** 0.2 — для более детерминированных, фактологичных ответов.
- **num_predict:** 512 — ограничение длины ответа, чтобы не "растекалась" мысль.
- **Системный промпт (`Modelfile`):** требует отвечать по-русски, короткими ответами с основанием, честно писать «В предоставленных материалах нет ответа», если данных нет, и не выдумывать файлы/настройки.
- **Агент `local-guide` (`demo/opencode.json`):** режим `primary`, права — только `read`, `glob`, `grep` (всё остальное `deny`), системный промпт из `demo/repo-system.txt` (требует указывать файл и строку для каждого факта, не придумывать выполненные команды).

## 4. Подготовка эталона: ещё один найденный лимит

По заданию эталон должен готовить «рабочий агент» OpenCode (режим Build, полные права), а не человек. Это пробовали сделать честно, локально, без облака:

- Первая попытка: `opencode run` из `lab/` без `--agent` — ушла в **облачную** модель `opencode/exo-free` (запрос упал с `Endpoint is unavailable`). Причина — в `lab/` нет своего `opencode.json`, конфиг с локальным провайдером лежит только в `demo/`, и без него OpenCode откатывается на дефолтный облачный провайдер. Это нарушало бы требование «модель должна работать на устройстве, а не через облачный API», поэтому результат не использовали.
- Вторая попытка, уже из `demo/` (там, где есть `opencode.json` с локальным `ollama/itmo-agent`): лог подтвердил `> build · itmo-agent` — то есть build-агент действительно пошёл через локальную модель. Но дальше агент **дважды подряд зациклился**: вызвал `Read test_service.py` с одними и теми же `offset/limit` три раза подряд и не дошёл до финального ответа за 240 секунд (таймаут). Отдельная причина: модель один раз попыталась прочитать `../service.py` вместо `./service.py` — промахнулась мимо относительного пути.
- Вывод: даже с полными правами тот же 3B-инстракт на CPU не смог устойчиво завершить простую агентную задачу «прочитать 2 файла и ответить на 5 вопросов» — зацикливание на повторном чтении, а не прогресс. Поднимать для этой роли более крупную `qwen3.5:4b` (как изначально предполагал `Modelfile.agent`, `qwen3.5:4b` + 64k контекста) не стали — именно эта модель и вызывала те самые 5–35-минутные зависания (см. раздел 2), так что `Modelfile.agent` остался неиспользуемым черновиком предыдущей идеи.
- Из-за этого `answers_reference.md` в итоге дособран вручную прямым разбором `demo/service.py` / `demo/test_service.py` (без обращения к какой-либо модели — ни локальной, ни облачной), с пометкой об этом в самом файле. Это отклонение от буквы задания («всю работу с файлами выполняет OpenCode»), но так честнее, чем выдавать зацикленный лог за готовый эталон.

## 5. Прогон 5 вопросов

Каждый вопрос тестируемой модели (`local-guide`, та же `itmo-agent`, но с правами только `read`/`glob`/`grep`) задавался **в отдельной новой сессии** (`opencode run --agent local-guide`), чтобы исключить утечку контекста между вопросами. Эталон (раздел 4) тестируемой модели не передавался.

| № | Вопрос | Ответ модели | Соответствие эталону |
|---|---|---|---|
| 1 | Как запустить тесты? Укажи файл-источник | «Файлы-источники... не указываются... найдите тестовый скрипт» | ✗ Не ответила по существу, не прочитала `demo/Makefile`, хотя `read`/`glob`/`grep` разрешены |
| 2 | Что будет при пустом имени? Подтверди кодом | «Files with relevant information not found» | ✗ Не нашла `service.py`, хотя файл лежит рядом |
| 3 | Где реализован unsubscribe? Проверь предпосылку | «Ты не указал файл, в котором нужно проверить предпосылку» | ✗ Переложила работу на пользователя вместо того, чтобы прочитать `service.py` и опровергнуть предпосылку (функции unsubscribe нет) |
| 4 | Какая CI-система запускает тесты? | «В данном репозитории нет указания на применение CI-системы» | ✓ Совпадает с эталоном — честно призналась, что данных нет |
| 5 | Сохраняются ли подписки после перезапуска? Подтверди кодом | «В данном контексте нет кода для подтверждения... зависит от настройки» | ✗ Фактически не ответила, не прочитала `service.py`, хотя там прямой ответ (`subscribers = set()`) |

**Главный вывод прогона:** на вопросы 4 (честное «не знаю») модель справилась хорошо — не придумала несуществующую CI. Но на вопросах 1, 2, 3, 5 она **не воспользовалась разрешёнными инструментами чтения файлов** и отвечала обтекаемо, фактически не прочитав код, хотя права `read`/`glob`/`grep` в агенте `local-guide` для этого есть. Это похоже на ограничение маленькой 3B-модели в агентном режиме через OpenAI-совместимый слой: она не инициирует tool-calls так надёжно, как через родной Ollama tool-calling API, и предпочитает текстовый ответ-отказ вместо вызова инструмента. На вопрос 3 (ложная предпосылка про unsubscribe) она не опровергла предпосылку явно, а просто ушла в сторону — тоже не идеальный результат, хоть и не выдумала код unsubscribe.

## 6. Демо случайного промпта на локальном сетапе

Вопрос вне списка пяти, та же схема (`local-guide`, новая сессия):

**Запрос:** «Что возвращает функция subscribe при успешном вызове? Приведи точное значение и укажи файл со строкой.»
**Ответ модели:** «В предоставленных файлах нет информации о функции subscribe или её поведении.»

Правильный ответ по коду: `{"subscribed": True}` (`demo/service.py:8`). Сетап при этом технически полностью рабочий — запрос ушёл в локальный Ollama (`itmo-agent`, CPU, без сети), ответ пришёл за секунды, без зависаний. Просто качество ответа низкое: модель не читает файлы, которые ей разрешено читать, и вместо этого отвечает «данных нет» даже когда они есть. Это тот же паттерн, что и в вопросах 1, 2, 3, 5 — честный, но неинформативный «отказ» вместо вызова инструмента.

## 7. Ограничения и выводы

1. **Thinking-модели плохо дружат с OpenAI-совместимым слоем** сторонних инструментов — отключение thinking может не долетать до модели, что превращает секундные ответы в десятки минут на CPU. Нужно тестировать транспорт, а не только модель.
2. **Маленькие instruct-модели (3B) в агентном режиме ненадёжны по части вызова инструментов** — даже имея права на чтение файлов, модель либо вообще не читает файл и отвечает «данных нет» (вопросы 1, 2, 3, 5, демо-промпт), либо зацикливается на повторном чтении одного и того же файла и не доходит до ответа (попытка собрать эталон тем же build-агентом, раздел 4). Для продакшен-агента это критично; для учебного стенда — показательный пример границ применимости локальных 3B-моделей в агентном режиме.
3. **Честность при нехватке данных (вопрос 4) отработала лучше**, чем активное использование инструментов — видимо, системный промпт с явным требованием писать «нет ответа» сработал надёжнее, чем ожидание, что модель сама решит пойти читать файлы. Обратная сторона: та же формулировка иногда маскирует не «данных действительно нет», а «модель поленилась их найти» (демо-промпт — наглядный пример).
4. Без GPU локальный инференс даже 3–4B моделей заметно нагружает CPU и RAM (наблюдался уход в swap), что стоит учитывать при выборе модели для машины без видеокарты.
5. Полностью локальный пайплайн работает (ни один ответ тестируемой модели не ушёл в облако), но подготовку эталона OpenCode своими силами выполнить не удалось (облачный фолбэк без локального конфига + зацикливание локальной модели) — эталон в итоге составлен вручную, это отдельно зафиксировано как отклонение от буквы задания.
