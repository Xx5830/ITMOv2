# Feature Specification: Поиск задач по части названия (API)

Created: 2026-10-28
Feature short name: title-search
Status: Draft

Input (from request): "Поиск задач по части названия: необязательный параметр q у GET /tasks, регистр не важен, пустой q даёт 400, работает вместе с параметром tag. Код не меняй."

## User Scenarios & Testing (mandatory)

### User Story 1 — Найти задачи по части названия (Priority: P1)

Как клиент API, я передаю параметр q и хочу получить только те задачи, в названии которых есть эта подстрока, без учёта регистра.

Acceptance scenarios:
1. Given задачи «Buy milk» и «Read book», When GET /tasks?q=milk, Then 200 и список из одной задачи «Buy milk».
2. Given те же задачи, When GET /tasks?q=MILK, Then результат как в п.1 (регистронезависимо).
3. Given любые задачи, When GET /tasks?q=zzz, Then 200 и пустой список [].
4. Given три совпадающие задачи, When GET /tasks?q=b, Then порядок в ответе совпадает с порядком создания.
5. Given любые задачи, When GET /tasks без q, Then возвращаются все задачи, как раньше (поведение без изменений).

### User Story 2 — Отвергнуть пустой запрос (Priority: P2)

Как клиент API, если я передаю пустой или состоящий из пробелов q, я должен получить понятную ошибку клиента, а не «показать всё».

Acceptance scenarios:
1. Given любые задачи, When GET /tasks?q=, Then 400 и JSON {"detail": "..."}.
2. Given любые задачи, When GET /tasks?q=%20%20, Then 400.

### User Story 3 — Совместить поиск с фильтром по тегу (Priority: P3)

Как клиент API, я могу одновременно фильтровать по подстроке названия и по тегу: условия объединяются по «И».

Acceptance scenarios:
1. Given задачи «Buy milk» [shop] и «Milk report» [work], When GET /tasks?q=milk&tag=work, Then только «Milk report».
2. Given q=milk&tag=, Then 400 (правило пустого tag действует как и раньше).

### Edge Cases

- q с пробелами по краям (" milk "): края отбрасываются, поиск идёт по "milk".
- Внутренние пробелы сохраняются: q=buy milk ищет подстроку целиком.
- q длиннее 100 символов после trim: 400 (названия не длиннее 100, совпадений быть не может).
- Спецсимволы (%, ., *) ищутся буквально, не как шаблон.
- Несколько значений ?q=a&q=b: берётся одно значение по общему правилу обработки повторяющихся параметров.

## Requirements (mandatory)

### Functional Requirements

- FR-001: GET /tasks MUST принимать необязательный параметр q.
- FR-002: При наличии q система MUST возвращать только те задачи, где q (после trim) входит в title без учёта регистра.
- FR-003: Порядок задач в ответе MUST совпадать с порядком их создания.
- FR-004: Пустой/пробельный q либо q длиннее 100 символов (после trim) MUST давать 400 с полем detail в теле ответа.
- FR-005: Параметр q MUST комбинироваться с параметром tag по логике «И».
- FR-006: При отсутствии q поведение GET /tasks MUST остаться прежним (возвращаются все задачи/или фильтр только по tag, если он передан).
- FR-007: При отсутствии совпадений система MUST возвращать 200 и пустой список [], не 404.

### Key Entities

- Task: {id: int, title: str, tags: list[str]} — без изменений.

## Success Criteria (mandatory)

- SC-001: Каждый acceptance-сценарий из историй 1-3 покрыт автотестом в `tests/`, и `sh scripts/check.sh` проходит полностью.
- SC-002: Поведение без q, а также существующие сценарии без параметра q сохраняются без регрессий (по результатам автотестов).

## Assumptions

- Поиск выполняется по полю title, без нормализации Unicode и без частичного совпадения по tags (только точные теги через параметр tag).
- Хранилище остаётся in-memory; ограничения производительности и объёма данных в рамках учебного проекта.
