# Общий контракт поиска (UI ↔ API)

Согласован между спекой логики (Spec Kit, `specs/002-title-search/`) и спекой UI
(OpenSpec, `openspec/changes/search-tasks-ui/`) до написания кода.

## Запрос
`GET /tasks?q=<текст>` - `q` необязателен. UI отправляет `q` уже после `strip`; пустой `q` UI не отправляет вообще.

## Ответы
| Код | Тело | Когда |
|---|---|---|
| 200 | `[{id, title, tags}]` в порядке создания | поиск выполнен; `[]`, если совпадений нет |
| 400 | `{"detail": "<строка>"}` | `q` пуст/пробельный или длиннее 100 символов |

## Состояния UI
| Ситуация | Что показывает UI |
|---|---|
| поле пусто | полный список (`GET /tasks` без `q`) |
| запрос идёт | индикатор «поиск…», граф не мигает |
| 200 и есть задачи | граф только по найденным задачам |
| 200 и `[]` | сообщение «ничего не найдено», граф пуст |
| 400 | текст `detail` под полем; граф не меняется |
| сетевая ошибка/таймаут 3 с | баннер из фичи B; граф остаётся прежним |

## Решения при согласовании
1. **Где фильтруем.** Только на сервере; клиентской фильтрации нет (принцип Authoritative Backend).
2. **Кеш localStorage.** Конфликт: фича B хранит «последний известный список». Решение: в кеш пишется только ответ
   на запрос без `q`, результат поиска кеш не перезаписывает - иначе после сбоя сети пользователь увидел бы «весь список» из трёх задач.
3. **Лишний 400.** UI не шлёт пустой `q`, но сервер всё равно отвечает 400 (защита от других клиентов).
4. **Debounce.** UI ждёт 300 мс после последнего ввода, чтобы не слать запрос на каждую букву.
5. **`tag` в UI.** В этой фиче UI параметр `tag` не использует; сервер его поддерживает (FR-005).
