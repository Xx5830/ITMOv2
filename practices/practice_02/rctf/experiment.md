# R.C.T.F.

- **Role:** инженер по производительности (performance engineer) в команде сервиса `/api/reviews` — AI-ассистента ревью PR. Отвечает за то, чтобы нефункциональные требования (латентность, устойчивость к нагрузке) были выведены из действующих инженерных правил, а не назначены на глаз. Не имеет права придумывать SLA, которых нет в документах команды — только выводить их из существующих правил и метрик.
- **Context:**
  - Правило `REL-1` (`CASE.md`): внешний LLM-вызов имеет timeout 10 секунд; ошибка превращается в контролируемый ответ.
  - Правило `API-1` (`CASE.md`): `diff` длиннее 20 000 символов отклоняется с HTTP 413.
  - Метрика из `problem.md`: целевая доля запросов с 5xx на `/api/reviews` — ≤ 1%.
  - Текущее состояние [`tests_load.md`](../../practice_01/tests_load.md): таблица задаёт `p95 latency ≤ 12с` без объяснения, откуда взялось число 12; `error rate ≤ 1%` без явной ссылки на источник; `20 RPS` и `5 RPS` в сценариях тоже не объяснены.
  - Ограничение: сервис внутренний, реальный профиль трафика ещё не собран (см. `problem.md`, метрика «собираем метрику»), поэтому нельзя опираться на исторические данные о нагрузке.
- **Task:** для каждого числового предела в таблице нагрузочных сценариев `tests_load.md` вывести явную формулу расчёта из `REL-1`/`API-1`/метрик `problem.md`. Если для числа нет вывода из правил — явно пометить его как инженерную оценку (допущение), а не выдавать за выведенный из правил факт.
- **Format:** таблица с колонками «Предел», «Значение», «Формула/источник», «Тип (правило / оценка)». Без сопроводительной прозы вне таблицы — сравнение должно быть считываемо построчно.

## Полный запрос

```text
Роль: ты performance-инженер сервиса /api/reviews, отвечающий за нефункциональные требования.
Тебе запрещено назначать SLA "на глаз" — только выводить их из действующих правил.

Контекст:
- REL-1: внешний LLM-вызов имеет timeout 10 секунд, ошибка -> контролируемый ответ.
- API-1: diff длиннее 20000 символов отклоняется с HTTP 413.
- problem.md, метрика "Доля запросов с 5xx": целевое значение <= 1%.
- Реальный профиль трафика ещё не собран (problem.md), исторических данных нет.

Задача: для каждого предела в таблице сценариев tests_load.md (p95 latency, error rate,
RPS в обоих сценариях, размер diff в граничном сценарии) выведи формулу из REL-1/API-1/
problem.md.

Разрешено: комбинировать несколько правил в одну формулу (например, timeout + оценка
overhead); явно помечать значение как инженерную оценку, если формулы из правил нет, и
указывать, на основании чего сделана оценка (например, сравнение с другим сценарием).

Запрещено: выдавать оценку без формулы за выведенное из правил значение; ссылаться на
"общие соображения о типичной нагрузке SaaS" или другие знания вне CASE.md/problem.md;
менять сами правила REL-1/API-1 или предлагать их пересмотр — это не входит в задачу.

Формат: таблица со столбцами "Предел", "Значение", "Формула/источник", "Тип (правило/оценка)".
Без текста вне таблицы.

Остановись и спроси человека, если: ни для одного разумного значения предела не находится
даже приблизительной формулы или базы для оценки в разрешённых файлах.
```

## Что получили

| Предел | Значение | Формула/источник | Тип |
|---|---|---|---|
| p95 latency (оба сценария) | ≤ 12с | `timeout(REL-1) = 10с` + оценка накладных расходов на валидацию входа и сетевое время ≈ 2с | Правило (10с) + оценка (2с) |
| Доля 5xx | ≤ 1% | `problem.md`, таблица метрик, строка «Доля запросов с 5xx на `/api/reviews`» | Правило (прямая цитата метрики) |
| Размер `diff`, граничный сценарий | ровно 20 000 символов | `API-1`, `CASE.md` — точная величина лимита | Правило (прямая цитата) |
| RPS, сценарий «Пиковая нагрузка CI» | 20 RPS | Нет вывода из `REL-1`/`API-1`/`problem.md` — оценка «разумное число параллельных CI-джобов» | Оценка (без формулы) |
| RPS, сценарий «Diff на границе лимита» | 5 RPS | Оценка от сценария «Пиковая нагрузка CI» (в 4 раза меньше, т.к. крупные diff реже обычных) | Оценка, производная от другой оценки |

## Что изменили в исходном артефакте

- Файл и раздел: [`tests_load.md`](../../practice_01/tests_load.md), таблица сценариев — добавлен столбец «Источник предела», а сами значения `p95`/`доля 5xx` явно выведены по формуле. Итоговая копия изменённого файла приложена рядом: [`tests_load.md`](tests_load.md).
- Изменение: `p95 ≤ 12с` теперь явно выведен как `timeout(REL-1) + overhead`, а не константа; `доля 5xx ≤ 1%` явно сослан на строку метрики в `problem.md`; значения RPS честно помечены как оценки без формулы, а не как выведенные из правил (это разграничение — прямой результат требования «Тип (правило/оценка)» в формате запроса).
- Как проверили: для каждого числа в таблице явно указано, правило это или оценка — ни одно число не выдано за большее, чем оно есть на самом деле.
- Что отклонили: предложение поднять `p95` до 15с «про запас» — отклонено, потому что не выводится ни из одного правила и увеличивает риск маскировать реальные regressions; попытку модели вывести формулу для RPS «из общих соображений о типичной нагрузке SaaS» — отклонена, так как это не источник из Context Pack, а общее знание модели.
