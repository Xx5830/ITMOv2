# Tree of Thoughts

- Решение, для которого нужны альтернативы: какой объём нагрузочного тестирования проводить для `/api/reviews` на текущем этапе (см. [`tests_load.md`](../../practice_01/tests_load.md)).
- Критерии выбора (с весами, чтобы оценка была не просто списком прилагательных):
  1. **Покрытие риска** (вес высокий) — насколько сценарий реально защищает от регрессий, описанных в `REL-1`/`API-1`.
  2. **Трудозатраты** (вес средний) — время инженера на подготовку и поддержку сценария.
  3. **Соответствие текущему трафику** (вес высокий) — не тратим ли мы усилия на моделирование нагрузки, которой ещё нет (`problem.md`: метрика трафика ещё не собрана).

## Запрос

```text
Роль: ты консультант по нефункциональным требованиям, который раскладывает решение на
явные альтернативы вместо того, чтобы сразу предлагать одно "правильное" решение.

Контекст: нужно решить, какой объём нагрузочного тестирования проводить для /api/reviews
на текущем этапе. Известно: правила REL-1 (timeout 10с) и API-1 (лимит diff 20000 символов)
из CASE.md действуют уже сейчас; метрика реального трафика в problem.md ещё не собрана
("собираем метрику"); сервис внутренний.

Задача: опиши три внешне разные альтернативы объёма нагрузочного тестирования - от "ничего
не делать" до "полный прод-реалистичный нагрузочный тест". Для каждой:
- дай конкретную реализацию (инструмент, длительность, кто делает, примерная трудоёмкость
  в часах или днях инженера);
- оцени по трём критериям (покрытие риска, трудозатраты, соответствие текущему трафику) по
  шкале 1-5, где 5 - лучший результат для этого критерия, и обоснуй каждую оценку одной
  фразой, а не только числом;
- укажи явный измеримый триггер, при котором именно эта альтернатива станет правильным
  выбором, даже если сейчас она не выбрана.

Разрешено: опираться на REL-1, API-1 и состояние метрики трафика из problem.md; предлагать
реалистичные инструменты (k6, locust и т.п.).

Запрещено: выбирать итоговую альтернативу самостоятельно - выбор и его обоснование сделает
человек по твоим оценкам; давать оценку критерия числом без текстового обоснования; описывать
альтернативы, которые на самом деле совпадают по объёму работ (они должны быть внешне разные).

Формат: таблица "Альтернатива | Реализация | 3 колонки-оценки | Триггер".
```

## Выбор

- Выбранная альтернатива: **B** — smoke-нагрузочный тест с порогами от `REL-1`/`API-1`.
- Почему (по взвешенным критериям): покрытие риска и соответствие трафику — критерии с высоким весом. У A высокая оценка по покрытию риска (4) формальна — она не подкреплена реальными данными (соответствие трафику = 1), то есть уверенность иллюзорна. У C оценки по трудозатратам/соответствию высокие, но это оценки от отсутствия действия, а не от качества решения — покрытие риска = 1 неприемлемо для двух правил (`REL-1`/`API-1`), которые уже нарушались в исходном diff `TRAINING_PR.diff`. B — единственная альтернатива без провала ни по одному из критериев с высоким весом (3 и 4 соответственно).
- Как проверим: колонка «Когда стала бы правильным выбором» уже фиксирует триггер пересмотра для каждой альтернативы — не нужно придумывать его отдельно. Для B → A: как только метрика трафика (`problem.md`) собрана и объём превысит порог из few-shot-эксперимента (100 запросов/неделю).
